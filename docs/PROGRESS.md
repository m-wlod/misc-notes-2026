Accounts ship switched off: with no Supabase env vars, sign-in shows "accounts aren't enabled", profile explains the same, settings and onboarding redirect to sign-in, and `/api/me/export` returns 401. Everything else (content, the placement quiz) works signed out. This is the state of Vercel previews today.

Blocked: the account's two free Supabase projects are in use by other apps and must not be touched, and the local Docker stack is unstable on this machine (the engine hung and returned HTTP 500).

When a project exists (a second Supabase account, or a paid plan), these are the steps:

1. **[you]** Create project `quant-learning-dev` in eu-central-1 (Frankfurt). Put in `.env.local` (never commit it): `NEXT_PUBLIC_SUPABASE_URL` (Settings → API), `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` and `SUPABASE_SECRET_KEY` (Settings → API Keys), `SUPABASE_DB_PASSWORD`, `SUPABASE_ACCESS_TOKEN` (Account → Access Tokens).
2. `supabase link` + `supabase db push`: migrations stay the single source of truth.
3. Point `test:db` at the dev project with test users the tests create and delete.
4. Write the signed-in e2e flows using `auth.admin.generateLink` instead of a mail catcher: magic link → onboarding → quiz → profile, anonymous merge, export, delete and re-sign-up, API isolation, axe on onboarding and settings; and (Phase 14) a correct answer showing the celebration and the header XP, the dashboard, the league page with two users, the profile radar and achievements.
5. **[you]** Auth → URL configuration: add `http://localhost:3000/api/auth/callback` and the Vercel URLs. Google and GitHub OAuth apps use the redirect URL `https://<project-ref>.supabase.co/auth/v1/callback`; then set `NEXT_PUBLIC_AUTH_PROVIDERS=google,github`.
6. **[you]** Vercel env (Preview + Production): the three Supabase vars above. Later, Resend as custom SMTP once the domain is verified.

## Resolved: "client re-render" of request-time pages under CI load (found in Phase 15)

CI e2e had 1–8 flaky tests per run since about Phase 11, all on request-time pages (sample exercises, `/dev/content-preview`, `/styleguide`), mostly dark theme on the mobile profile; in Phase 15 three failed both attempts. The trace of a failure (kept since Phase 12) settled it: the page was still **mid-stream**. React puts a Suspense boundary's streamed content in a hidden `<div id="S:n">` and a `<template id="B:n">` placeholder in `<main>`, then an inline script swaps it in; under CI load that swap lagged behind the `load` event, so locators found the content twice or not yet in place (the "server copy beside client ids, empty `<main>`" seen in Phase 12 was this state, not a client re-render). Users never see the hidden copy.

- **Fix (tests):** every spec imports `test` from `e2e/test.ts`, whose `page.goto` / `page.reload` wait until no `S:`/`B:` streaming markers remain. 166 tests ran twice each at 4 workers with no retries and no failures.
- **The "no flash" tests** (fixed in 12b) were a different cause and stay as they are.
- **Still worth a look in Phase 20:** pages that stream late on slow phones show their skeleton for longer; that's performance, not correctness.

## Known issue: Next.js hydration race on early clicks

Investigated in Phase 8b. On a heavy page, a link clicked in the short window between `load` and React hydration can be cancelled. Next.js calls `history.replaceState` for the current URL when hydration finishes, and Chrome then aborts the navigation already under way. Reproduced 4/4 on the sample lesson preview with an immediate click, with both `<Link>` and a plain `<a>`, and with `partialPrefetching` on or off. After hydration, every navigation tested took 60–195 ms (16/16). Real users rarely click within that window, but slow phones widen it. It's framework behaviour, not ours. Revisit when upgrading Next, and in the pre-launch performance pass (smaller hydration cost shortens the window). The e2e tests wait for the page to settle before navigating.
